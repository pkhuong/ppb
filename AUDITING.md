# Auditing PPB

PPB is a small, allocation-free C11 lexer for protobuf binary
encoding, intended to run on untrusted input. `SECURITY.md` describes
the threat model, what is verified, and what callers must do; the
`README.md` describes how to use the library. This document is written
for an integrator who has decided to vendor PPB and wants to
*independently confirm* the claims made in the documentation: each
section pairs a claim with a simple path to re-verify it from a
checked-out tree. This document is about claim verification, not a
line-by-line code review.

If a claim appears here without an accompanying recipe (a command, a
make target, a test name, or a reference to the source), that's a doc
bug; please report it.

## Pinned-revision workflow

PPB has no SLA and a single maintainer; it's also not a lot of
code. Vendor it at a specific commit and audit that.

1. **Pin a commit.** Embed the SHA in your build (a git submodule, a
   `.tar.gz` keyed by SHA, or a vendored copy in your tree). Don't
   track `main`; pin to a specific revision you have audited.
2. **Run `make test` in a clean checkout** at that SHA.  CI already
   does that on GitHub, but it makes sense to confirm for your
   specific toolchain.  Save the successful test output.
3. **Run `make wp` in a clean checkout** at that SHA. Confirm the
   output matches expectations (see [Frama-C coverage](#frama-c-coverage)
   for what counts as expected, including the contents of `wp.csv`
   and the [admit ledger](#admit-ledger)). Save the output and
   `wp.csv` alongside your vendored copy.
4. **Run `make fuzz` for as long as your risk budget allows.** The
   default target runs only 60 seconds with `max_len=1024`; for
   production vendoring, override the duration and any libFuzzer
   flags you need:

   ```sh
   make fuzz FUZZ_TIME=3600 FUZZ_MAX_LEN=4096 \
       FUZZ_FLAGS='-jobs=8 -workers=8'
   ```

   The Makefile exposes `FUZZ_TIME`, `FUZZ_MAX_LEN`, and `FUZZ_FLAGS`
   as overrides; everything else (sanitizers, harness) is fixed. Save
   coverage and any crash artifacts alongside the WP output.

The sections below are the recipes referenced by the steps above.

## Project shape

- Public API: `include/ppb/ppb.h`. The `_with_hard_limit` /
  `_with_soft_limit` variants are `static inline` wrappers around
  `ppb_prescan_impl` / `ppb_lexn_impl`.
- Implementation: `src/ppb.c` plus the private headers `src/buf.h`,
  `src/varint.h`, `src/error.h`, `src/sat_sub.h`, `src/cc.h`.
- Unit tests: `tests/test_ppb.c` (compiles `src/ppb.c` directly, so
  it can reach internal symbols).
- Golden tests: `examples/picoscope.c` driven by
  `test_picoscope.sh`; valid cases in `testdata/`, invalid cases in
  `testdata/invalid/`. Outputs are diffed against
  [protoscope](https://github.com/protocolbuffers/protoscope).
- Fuzz harness: `fuzz/fuzz_ppb.c` (libFuzzer); seeds in
  `fuzz/corpus/` are generated by `fuzz/gen_corpus.py`.
- Frama-C build: driven by `frama-c.mk`, runs in a Docker image
  built from `.docker/`. WP entry point `ppb_entry_point` lives in
  `src/ppb.c` under `#ifdef __FRAMAC__`.
- Schema generator: `generator/protoc_gen_ppb.py`, a `protoc` plugin
  that emits `ppb::schema` headers from `.proto` files; checked by
  `make generator_test` (lint, type-check, pytest, golden headers,
  compilation of the generated schemas).
- Differential / conformance: `differential/` decodes through
  generated schemas into libprotobuf messages and compares against
  libprotobuf's own parser; see
  [Generated schemas vs. libprotobuf](#generated-schemas-vs-libprotobuf).

## Verification recipes

The recipes below run against a built `build/libppb.a`. Build it once
with `make build/libppb.a`.

### No allocation, no dependency except assert

PPB never allocates heap memory. `nm` is the cleanest check: an
allocator call would show up as an undefined reference.

```sh
nm --undefined-only build/libppb.a

ppb.o:
__assert_fail
```

The only undefined references should be assertion handlers
(`__assert_fail`, `__assert_rtn`, or the equivalent for your libc)
and, with `-fstack-protector` on GCC, `__stack_chk_fail`. These are
optional libc dependencies and none of them can trigger memory
allocation. Building with `EXTRA_FLAGS=-DNDEBUG` and without stack
protection eliminates them entirely:

```sh
nm --undefined-only build/libppb.a
# nothing
```

### No mutable global state

PPB is reentrant and trivially thread-safe: no mutable file-scope
storage. Confirm with `nm`, looking for writable data symbols (`B`
bss, `D` data, `G` small init data, `C` common, and their lowercase
local variants). Read-only data (`R`/`r`) is fine: that's just
`static_assert` strings and similar.

```sh
nm build/libppb.a | awk '$2 ~ /^[BbCDdGg]$/'
```

Expected: no output.

### Wire types 3, 4, 6, 7 rejected

```sh
grep -n 'PPB_ERROR_CORRUPT_TAG' src/ppb.c
```

The wire-type switch in `handle_field` covers `case 3` (legacy
SGROUP), `case 4` (legacy EGROUP), and the `default` (for wire types
6 and 7); `ppb_prescan` also rejects field number 0 in any encoding
(canonical `0x00-0x07` or overlong), while `ppb_lexn` rejects only
the canonical single-byte encodings. Tested
directly by the
`testdata/invalid/group-start`, `testdata/invalid/group-end`,
`testdata/invalid/bad-wiretype-6`, and
`testdata/invalid/bad-wiretype-7` golden cases (driven by
`test_picoscope.sh`).

### Memory safety, termination, progress

```sh
make wp
```

Expected output: every reported goal `Valid`, except the `admit`
clauses listed in the [Admit ledger](#admit-ledger) below and the
three builtin conditions tracked in `wp.csv` (see [Frama-C coverage](#frama-c-coverage)).

### ACSL postconditions exercised dynamically

```sh
make fuzz                  # 60-second smoke test
make fuzz FUZZ_TIME=3600   # one hour
```

Runs libFuzzer under ASan + UBSan. The harness re-checks ACSL
postconditions at runtime (`POSTCOND` macro in `fuzz/fuzz_ppb.c`); a
mismatch traps via `__builtin_trap()`. See the admit ledger for which
fuzz check covers which admit. See [Pinned-revision workflow](#pinned-revision-workflow)
for the override knobs.

**LEN payload readability is formally verified.** WP discharges the
`/*@ assert buf_valid_range(dst->v.payload); */` in `handle_field`
(see wp.csv).  Every decoded `field.v.payload` is therefore a readable
subrange of the input buffer.

The fuzz harness and `picoscope` dynamically check stronger placement
properties not expressed in ACSL:

- **`field.v.ptr` within consumed input.**
  `check_prescan_fields_in_range` asserts all non-null `v.ptr` lie in
  `[data, data + returned_byte_count)`;
  `check_lexn_fields_in_range` asserts `buf_before <= v.ptr < buf_after`
  (`buf->buf` before/after the call).
- **LEN payload within consumed input.** The same helpers bound
  `payload.buf` and `payload.buf + payload.size` by that range.
- **Payload after tag byte.** The dynamic checks assert
  `payload.buf > v.ptr` on every decoded LEN field.

Any regression traps immediately, regardless of sanitizers.

### Generated schemas vs. libprotobuf

The `protoc-gen-ppb` generator and the C++ wrapper sit outside the WP
proofs; the claim that generated schemas decode like libprotobuf is
empirical.  Unlike the recipes above, these need protoc, libprotobuf,
and `uv`, and the containerized conformance run needs Docker; the
targets print a skip message when a dependency is missing:

```sh
make differential-ci                     # deterministic subset, same as CI
make -C differential conformance-docker  # conformance suites, in a container
```

`differential-ci` runs fixed-input and pseudorandom reflection
differentials plus fuzz-corpus replays, with no Docker and no
time-bounded fuzzing.  The conformance run drives Google's
`conformance_test_runner` over three testees (proto3 full, proto2,
proto3 lean) against the failure lists in `differential/`: expect
zero unexpected failures, with the proto3 full list empty, the proto2
list holding only the group-based `MessageSet` cases, and the lean
list holding the deliberate strict-encoding rejections.  Every listed
failure is tagged and explained in `differential/GAPS.md`.

## Frama-C coverage

The Docker image is pinned to Frama-C 32.0 (codename
[Germanium](https://www.frama-c.com/fc-versions/germanium.html)).  The
flags below are passed in `frama-c.mk`; each one's role and its
practical effect on the PPB proof are summarized here so an auditor
who is not a Frama-C user can read the makefile invocation end-to-end.

| Flag | Role | Effect on PPB |
|------|------|---------------|
| `-machdep=gcc_x86_64` | Selects the C ABI (sizes, alignments, signedness of `char`) modeled by the analyzer. | Pins the proof to the gcc x86-64 ABI. Other CI targets (i686, aarch64, s390x) are covered by sanitizers only. |
| `-wp` | Runs the WP plugin. | Discharges memory-safety, termination, and the named behavioral goals to SMT solvers. |
| `-wp-rte` | Generates runtime-error checks (signed overflow, division by zero, invalid shifts, pointer arithmetic OOB). | Adds the obligations PPB needs in order to claim "no UB": pure-ACSL contracts otherwise wouldn't generate them. |
| `-wp-smoke-tests` | Asks WP to prove `\false` from each contract; success means the contract is satisfiable, failure flags an inconsistent contract. | Catches the classic "vacuously true" failure mode where a contradictory `requires` would let WP prove anything. |
| `-wp-model="typed+var+int+float+ref"` | The Hoare memory model. `typed` is the typed-pointer model; `var` separates address-taken locals; `int` and `float` lift machine arithmetic to mathematical integers/reals where sound; `ref` enables alias-free reasoning across `restrict` parameters. | Tractable for PPB's pointer arithmetic into a single `ppb_buf`; relies on the `__restrict` qualifiers in the public API. Models other than `typed` (e.g., `bytes`) would have more trouble discharging the buffer-validity predicates. |
| `-wp-status` | Reports an explicit per-goal status in the output. | Lets the post-run report classify exactly which goals were `Valid`, `Unknown`, `Invalid`. |
| `-instantiate` | Enables ACSL `instantiate` directives. | Used implicitly by some lemmas; harmless for PPB. |
| `-constfold` | Folds constants in preprocessed source before analysis. | Lets WP see the encoded values of macros like `PPB_TAG_BITS(1, ...)` literally. |
| `-lib-entry` | Analyzes the file as a library: no `main`, and global state at entry is arbitrary. | Every annotated function is verified against its own contract; PPB has no mutable globals, so the arbitrary-globals part changes nothing. |
| `-cpp-extra-args="-I include -isystem stubs-for-frama-c -std=c2x -DNDEBUG"` | Preprocessor setup for the analyzed translation unit. | `stubs-for-frama-c/` supplies the `immintrin.h` stub that selects the BMI2 fast path (see [Code paths actually proven](#code-paths-actually-proven)); `-DNDEBUG` compiles the `assert`s out, so the proof covers the assertion-free build. |
| `-wp-split-conj` | Recursively splits conjunctions in generated goals into separate sub-goals. | Goal granularity only: more, smaller goals for the solvers; no change to what is claimed. |
| `-wp-no-callee-precond` | Skips the extra hypothesis that a callee's preconditions held after a call returns; the obligations to *prove* those preconditions at each call site are generated either way. | Strictly fewer hypotheses: a sound restriction that keeps proof contexts small. |

The remaining flags in `frama-c.mk` (`-session`, `-cache-size`,
`-memory-footprint`, `-wp-session`, `-wp-cache`, `-wp-par`,
`-wp-timeout`, `-wp-prover`) select the SMT-solver fleet and cache
proof sessions; they affect wall-clock time, not what is proven.
`WP_FCT` (forwarded as `-wp-fct`) restricts a run to named functions
for quicker iteration and is empty for audit runs.  The trailing
`-report-*` flags write the `wp.csv` report discussed below;
`-report-no-proven` keeps `Valid` goals out of it.

### Expected `wp.csv` content

`make wp` finishes by writing a `wp.csv` report at the repo root
(`make clean` deletes it); the report lists every obligation flagged
as not `Valid`.  A run against this tree records exactly three rows:

```
FRAMAC_SHARE/libc  __fc_gcc_builtins.h  131  __builtin_usubl_overflow  postcondition       Unknown  \false
FRAMAC_SHARE/libc  __fc_gcc_builtins.h  131  __builtin_usubl_overflow  termination clause  Unknown  \true
FRAMAC_SHARE/libc  __fc_gcc_builtins.h  262  __builtin_ctzll           termination clause  Unknown  \true
```

These are not PPB obligations: they are the postcondition and
termination clauses on Frama-C's stubs for two gcc builtins
(`__builtin_usubl_overflow`, used in `src/sat_sub.h`;
`__builtin_ctzll`, used in the varint / tag fast paths). The stubs
have no body, so WP cannot discharge either; the contracts match the
documented gcc semantics, so we trust them. A rerun should produce
exactly these three rows. Any other row is a PPB regression and must
be triaged.

### Code paths actually proven

There are two versions of `squish_varint`.  The Frama-C analysis
defines `__BMI2__` (via `immintrin.h` in the stubs directory) and so
proves the BMI2 version.  That's not a problem for WP coverage because
`squish_varint_portable` has the same contract, and the contract isn't
very useful anyway.

The two implementations are kept equivalent by testing only:
- `tests/test_ppb.c::test_squish_varint_equivalence` calls both on
  a static set of inputs and asserts equality.
- The varint round-trip tests in `tests/test_ppb.c` and the fuzz
  harness exercise whichever variant is active for the build.

## Caller checklist

When integrating PPB to parse untrusted input, a wrapper author must
satisfy all of the following.

- [ ] **Cap submessage nesting depth** in caller code. PPB is
      iterative within a single message level; recursive descent on
      `PPB_WIRE_LEN` submessages is the caller's responsibility.
      Unbounded recursion has been a recurring CVE source in the
      protobuf ecosystem ([CVE-2024-7254](https://github.com/advisories/GHSA-735f-pc8j-v9w8),
      [CVE-2026-0994](https://github.com/advisories/GHSA-7gcm-g887-7qv7)).
- [ ] **Install catch-alls (one per wire type) if you need strict
      wire-type checking.** PPB matches tags by full encoded form, so
      a wire-type mismatch on a known field number silently falls
      into the matching catch-all (or is skipped). See
      `README.md` "Strict wire-type checking" for a worked example.
- [ ] **Validate `field.v.payload.size`** before any downstream
      allocation. The size is attacker-controlled; PPB itself only
      checks that the payload fits in the input buffer.
- [ ] **Discard `fields[]` after any negative status.** On error,
      the contents of `fields[]` are unspecified (safe to read, but
      otherwise meaningless); `*buf` points somewhere within the
      offending field. PPB does not support resumption.
- [ ] **Never alias** `tags[]`, `fields[]`, and the input buffer.
      The `restrict` qualifiers on the public API document this.
- [ ] **Zero-initialize `fields[]`** before the first call on a
      given message. Zeroing also lets `field.v.ptr != NULL` work as
      a "field was decoded" predicate after a one-shot `ppb_prescan`.
- [ ] **Clamp `ppb_buf.size ≤ PTRDIFF_MAX`.** Larger objects
      introduce well-known UB in C
      ([Pascal Cuoq's writeup](https://www.trust-in-soft.com/resources/blogs/2016-05-20-objects-larger-than-ptrdiff_max-bytes)).
      On 64-bit hosts this rarely constrains anything, but it's
      still good to validate.
- [ ] **Call `ppb_validate_tags`** once at startup on every static
      `tags[]` array. Skipping this does not cause UB but can
      produce wrong output (or, in builds with assertions, an
      assertion failure).

## Admit ledger

PPB's ACSL annotations include ten `admit` clauses that WP cannot
discharge but which are sound by inspection. Many are paired with a
runtime check (a unit test or a fuzz postcondition) so the property
fails loudly if it stops holding. The table is exhaustive: any `admit`
not listed below is a doc bug.

Each row's "Name" column matches the label written on the `admit`
clause in source. To jump straight to the site, grep for the name:

```sh
grep -nEA2 'admit\b.*\b<name>\b' src/ppb.c src/varint.h
```

(e.g., `grep -nEA2 'admit\b.*\bzero_absent\b' src/ppb.c src/varint.h`).

| # | Name | Site | Property | Soundness sketch | Dynamic check |
|---|------|------|----------|------------------|---------------|
| 1 | `bitor_ge_l` | `src/ppb.c` | `(a \| b) ≥ a` | Bitwise OR can only set bits, never clear them; for unsigned integers this monotonicity gives the inequality. WP lacks a built-in axiom for this. | None: an arithmetic identity with no runtime counterpart to check. |
| 2 | `sint32_in_range` | `src/ppb.c` (`sint32` behavior of `ppb_zag`) | For `0 ≤ x < 2³²`, `ppb_zag(x) ∈ [-2³¹, 2³¹)` | `ppb_zag` is `(x >> 1) ^ -(x & 1)`. For `x < 2³²`, `x >> 1 < 2³¹`, and XOR with `-(x & 1) ∈ {0, -1}` either leaves the value or bit-inverts it; both stay in the signed-32-bit range. | `tests/test_ppb.c::test_zag` boundary cases; `fuzz/fuzz_ppb.c::fuzz_zag` re-checks the bound on every iteration. |
| 3 | `tags_above_seven_induction` | `src/ppb.c` (`ppb_validate_tags`) | After the loop, `∀ j. 0 ≤ j < num_fields ⇒ tags[j].bits > 7` | `tags[0].bits ≥ 8` is checked before the loop, and the loop body rejects any `tags[i-1].bits ≥ tags[i].bits`. Strict ascending order plus a base case ≥ 8 implies every element is > 7. WP cannot fold this universally-quantified induction automatically. | `tests/test_ppb.c::test_validate_tags` (and the sentinel variants) exercise both the base case and every rejection path the induction rests on. |
| 4 | `pivot_dominates_suffix` | `src/ppb.c` (`find_tag`, `well_formed` clause) | At a binary-search pivot: `tags[lo+pivot].bits > tag ⇒ ∀ i ∈ [lo+pivot, num_fields). tags[i].bits > tag` | Sortedness: in a strictly ascending array, if the pivot exceeds `tag`, so does every element after it. WP's induction support cannot generalize from the pivot to the suffix. | The cross-validation in `fuzz/fuzz_ppb.c::cross_validate_meta` and the explicit prescan / lexn equivalence checks would surface a mis-routed tag (a tag landing on the wrong field). `tests/test_ppb.c::test_validate_tags` and the per-tag matching tests cover the search behavior. |
| 5 | `zero_absent` | `src/ppb.c` (`well_formed` clause of `ppb_prescan_impl`) | `tag < 8 ⇒ field_idx ≥ num_fields` | `well_formed` assumes `∀ j. tags[j].bits > 7`. `find_tag`'s postcondition states `field_idx < num_fields ⇒ tags[field_idx].bits ≡ tag`. Contrapositive: if `tag < 8`, no `tags[j]` matches, so `field_idx ≥ num_fields`. | Implicit: the prescan loop returns `PPB_ERROR_CORRUPT_TAG` for any field-0 tag (the field-number mask catches overlong encodings too). Unit tests `test_prescan_zero_tag` / `test_prescan_field_zero_overlong` and golden cases `testdata/invalid/tag-zero.hex` / `tag-zero-overlong.hex` confirm the detection. |
| 6 | `tag_above_seven_after_match` | `src/ppb.c` (`well_formed` clause of `ppb_prescan_impl`) | `tag > 7` at the call to `handle_field` | The tags array only has values `> 7`; a hit can only be for a `tag > 7`. | None of its own: implied by `tags_above_seven_induction` (all validated tags exceed 7) and `zero_absent` (`tag < 8` returns early), whose checks are listed above. |
| 7 | `lexn_buf_valid_after_copy` | `src/ppb.c` (`ppb_lexn_impl` ensures) | After the function returns, `buf_valid(*buf)` holds | The loop invariant maintains `buf_valid(src)`. The final statement is `*buf = src;`. WP has trouble with the struct copy. | `fuzz/fuzz_ppb.c::check_buf_valid` re-checks the invariant after every `ppb_lexn*` call: `buf.size <= input_size` and `buf.buf + buf.size == input + input_size`. A regression would trap. |
| 8 | `lexn_meta_unchanged_in_loop` | `src/ppb.c` (`ppb_lexn_impl` loop body) | `∀ j. fields[j].m ≡ \at(fields[j].m, Pre)` after `handle_field` with `update_metadata=false` | With `update_metadata=false`, `handle_field`'s `nometa` behavior assigns only `dst->v`, `*src`, and `*error`, never any `fields[j].m`. WP has trouble tracking that exclusion through the `dst`-pointer indirection. | `fuzz/fuzz_ppb.c::do_lexn_call` (and the hard / soft variants) snapshots `fields[].m` before each call and re-checks equality after via `check_lexn_postconds`. |
| 9 | `lexn_meta_unchanged_in_loop_again` | `src/ppb.c` (`ppb_lexn_impl` loop body, error-break path) | Same property as #8, re-stated after the `dst->v = (struct ppb_field_value) { .ptr = NULL };` zero-fill on the error path | The zero-fill assigns through `dst->v` only; the `m` field of `*dst` (and every other `fields[j].m`) is untouched. Together with #8 this preserves the metadata invariant across the error `break`. WP cannot see that the struct-literal write to `dst->v` definitely doesn't bleed into any `.m` field, so the property must be re-admitted. | Covered by the same `fuzz/fuzz_ppb.c::do_lexn_call` snapshot/check as #8. Fuzzing exercises the error path whenever the input is malformed mid-buffer. |
| 10 | `peek_tag_fits_63` | `src/varint.h` (`peek_tag` ensures) | On success, `*OUT_tag < 2⁶³` | The fast path reads ≤ 8 bytes with `limb_width = 8`. If there's no stop bit in the first 8 bytes, we return an error. Otherwise the worst case is only the eighth byte has its stop bit clear, so it contributes at most 7 bits in positions [62:56]. All 8 bytes together yield at most 63 bits. | `tests/test_ppb.c::test_peek_tag_range` checks the boundary case directly. |

A surviving admit means: WP's automated provers failed to discharge
the proof obligation. The ten admitted assertions above are basic
arithmetic identities that SMT solvers have trouble with, simple
induction over bounded arrays, or structural facts about pointer
aliasing that are hard to verify with the typed memory model's
separation logic.  For the structural pointer-aliasing facts in
particular, dynamic checks let us re-confirm the invariants via
fuzzing.

## What PPB will not protect against

Even when the checklist above is satisfied, PPB makes no claim about
the following.  Keep that in mind when designing an integration.

1. **Resource exhaustion via caller-chosen budgets.** `num_fields`,
   `max_lexed_fields`, and any byte limit you pass in are *your*
   policy choices; PPB does not second-guess them.
2. **Schema-level semantic validity.** Type confusion across fields,
   `oneof` violations, missing required fields, and similar concerns
   are caller responsibilities. PPB enforces wire format only.
3. **Side channels.** PPB is not constant-time. Varint length and
   field-dispatch are data-dependent.
4. **Anything outside the verified targets.** WP holds for
   `gcc_x86_64` only; see [Frama-C coverage](#frama-c-coverage).
5. **Concurrent mutation of the input buffer.** Buffers must be
   read-only for the duration of a call.
6. **Mixed-endian / VAX-endian hosts and compilers other than
   gcc / clang.** Best-effort at most.

## Resource bounds

Numbers below were measured at commit `6777f8b` with `gcc 12.3.0` on
`x86_64`, compiled with `-O2 -std=c11`. Re-measure on your target
platform with:

```sh
gcc -O2 -Iinclude/ -std=c11 -fstack-usage -c -o /tmp/ppb.o src/ppb.c
cat /tmp/ppb.su
```

Setting or clearing `-mbmi2` does not change the numbers (the BMI2
fast path inlines into `peek_varint` / `peek_tag` and does not
introduce additional local storage).

### Per-function stack frames

| Function            | Frame (bytes) |
|---------------------|---------------|
| `ppb_validate_tags` | 8             |
| `peek_varint_slow`  | 24            |
| `ppb_decode_varint` | 64            |
| `handle_field`      | 80            |
| `ppb_prescan_impl`  | 208           |
| `ppb_lexn_impl`     | 240           |

### Worst-case call chains

The deepest stacks are:

- `ppb_lexn_impl -> handle_field -> peek_varint_slow`: 240 + 80 + 24 = **344 bytes**
- `ppb_prescan_impl -> handle_field -> peek_varint_slow`: 208 + 80 + 24 = **312 bytes**

### Time complexity

Iteration counts on the `peek_varint_slow` loop are bounded
structurally by the loop header `for (size_t shift = 0; shift < 64;
shift += limb_width)` in `src/varint.h` with `limb_width ∈ {7, 8}`:

- ≤ 10 iterations for varints (`limb_width = 7`, shift sequence
  `0, 7, 14, 21, 28, 35, 42, 49, 56, 63`).
- ≤ 8 iterations for tags (`limb_width = 8`, shift sequence
  `0, 8, 16, 24, 32, 40, 48, 56`).

That's constant time.

There's no loop in `handle_field` or `ppb_decode_varint`.

Both `ppb_prescan` and `ppb_lexn` run in `Θ(n log m)` where `n` is the
number of toplevel fields consumed and `m` is `num_fields` (`O(log m)`
from binary search in `find_tag`); payload sizes for length-prefixed
fields don't enter the bound.

Finally, `ppb_validate_tags` is a single `for` loop over the input
array (linear time).

### Recursion

PPB itself is non-recursive: a single `for` loop in `ppb_prescan_impl`
and another in `ppb_lexn_impl` (both in `src/ppb.c`). Callers must
handle submessages, and should impose a limit on recursion depth
(see the worked example in `README.md`).
